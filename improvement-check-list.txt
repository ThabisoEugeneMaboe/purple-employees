I've reviewed the notes against the existing Mivali Purple application and its current prototype functionality.

The most important distinction is between:

- Clear improvements we can implement now within the existing application.
- Improvements requiring further clarification, particularly around confidentiality, recipient selection, unions, and external support.
- Items that belong to a later development stage, such as secure identity protection, external integrations, and operational escalation.

We should avoid implementing features in a way that appears to guarantee confidentiality when the prototype does not yet have the security controls to enforce it.

## Mivali Purple – Development Improvement Checklist

This checklist separates changes that can reasonably be implemented now from requirements that need clarification or belong to backend/security development.

## 1. Clear improvements suitable for the existing application

These can be addressed within the current prototype without fundamentally changing its architecture.

Visual improvements

- Pictures and illustrations: Introduce appropriate visual elements to make the employee interface more engaging and easier to understand.
- Colour-coding: Apply consistent colours to distinguish support pathways and, where appropriate, request statuses.
- Sidebar identification: Clearly identify the application in the sidebar using the Mivali Purple branding instead of relying exclusively on the logo.

Employee support experience

- Recipient selection interface: Introduce a recipient-selection step or interface in the employee request journey, subject to confirming the available recipient categories.
- Alternative reporting option: Provide a visible indication that employees can seek assistance through an alternative route when their immediate manager or usual recipient is implicated.
- Independent support pathway: Continue developing the existing independent-support pathway so that employees can understand and select it as an alternative to workplace support.

Existing prototype refinement

- Ensure the four support pathways remain clearly distinguishable:
  - Emotional support
  - Workplace concerns
  - Independent support
  - Retaliation support
- Review the employee journey to ensure the available support options are understandable and accessible.

## 2. Requirements that need clarification before implementation

These are understandable in principle, but the operational details must be established first.

### Recipient selection and routing

- Define the different categories of people or roles who may receive employee requests.
- Determine which recipients employees may select themselves.
- Establish how requests are assigned when employees do not select a recipient.
- Define the alternative reporting route when a manager, supervisor, or intended recipient is implicated.
- Establish safeguards preventing an implicated person from receiving, accessing, or controlling the relevant request.

### Union involvement

- Clarify whether unions should be recipients, independent support providers, escalation options, or some combination.
- Establish whether union involvement should be optional or initiated through a specific support pathway.
- Confirm the practical arrangements before implementing union-related workflows.

### Employee rights and escalation

- Determine what information employees should receive concerning their rights.
- Define the available escalation options and circumstances under which they may be used.
- Establish what information the application should communicate about escalation without presenting unverified legal guidance.

### Employee references and confidentiality

- Define how employees should be identified within support requests.
- Establish whether employee reference numbers should be generated by the system or supplied by employees.
- Determine whether employees should register a separate reference number or identification code.
- Establish who can access the information connecting employee identities to their references.
- Define how employee names should be hidden from support personnel where appropriate.
- Establish access restrictions ensuring employees cannot view other employees' requests.

Important: Using employee references instead of names is a useful confidentiality measure, but it does not by itself guarantee anonymity. The underlying identity information and access permissions must also be protected.

## 3. Improvements belonging to backend and integration development

These are valid requirements, but they depend on additional technical work.

- External support integration: Explore integration with external support systems once providers and arrangements are established.
- Independent support API: Establish an API or other secure communication mechanism between Mivali Purple and an independent support system, if required.
- Secure identity management: Implement appropriate authentication and identity protection.
- Role-based access: Ensure employees, internal support personnel, external support providers, and administrators have appropriate access permissions.
- Confidential request access: Enforce request-level access restrictions so unauthorised employees and personnel cannot access confidential requests.
- Secure alternative routing: Implement routing and escalation safeguards for requests involving implicated managers or other recipients.

## 4. Items excluded from this implementation checklist

- More-information link under "Your message": Excluded from the current implementation scope, as previously decided.

## 5. Recommended development order

Suitable for current prototype

1. Improve visual presentation, pictures, colour-coding, and sidebar branding.
2. Review and refine support pathway presentation.
3. Introduce the recipient-selection interface once recipient categories are sufficiently defined.
4. Make alternative reporting and independent support options more clearly accessible.
5. Continue refining the existing employee request and internal-support workflows.

Requires requirements clarification

6. Confirm recipient roles and request-routing rules.
7. Clarify union involvement.
8. Define employee identification and confidentiality requirements.
9. Confirm employee rights and escalation information.

Backend and security stage

10. Implement secure identity management and role-based access.
11. Implement confidential request access and alternative routing safeguards.
12. Develop external-support integration and API communication where required.

My recommendation: We can begin with the visual improvements and employee-facing interface refinements. Recipient selection is also a reasonable next feature, but we should establish the recipient categories and alternative reporting rules before implementing actual request routing. This keeps development moving without prematurely committing to an unclear support structure.
